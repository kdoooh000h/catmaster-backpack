# 按分支决定深度的目录试验

2026-10-15。自适应候选在已测的 **6 条正向需求中全部选对**，每一步都保留了标准答案；
其中一题要求先配置 Jira、再建立医疗器械质量体系，后一项的正确能力也保留到了终选。
这是公开 Skill 指导的选择测试，没有安装能力或执行这些业务任务。

共同完成的五题上，自适应比一直展开到叶子的方案平均少 25% 的调用，耗时低 22.24%。
总 token 表面上低 7.08%，但大部分来自一题目录评分波动；排除该题的事后检查中，
token 仅低 0.17%，基本持平。**少走几轮已经有初步效果，稳定减少 token 尚未证实。**

本轮达到预设用量上限后停止，两个负向控制未执行；尚不能声称完整验收或最佳方案。
日常目录、最终门槛和生命周期均未修改，代码仅是隔离试验。

## 分类与选择如何改变

继续使用固定的 376 项公开能力、原始需求和完整终选描述。来源为
[claude-skills 固定提交](https://github.com/alirezarezvani/claude-skills/tree/19392f7a08264ed00486a251f5b2098321771f94)。
分类作者已知旧题，因此这不是独立盲测，也不是新需求的泛化准确率。

先前的自动树把许多来源和关键词混在一个目录描述中，模型难以排除分支。
本次保留 6 个根类和 20 个来源分类，在七个大来源类别下增加完整的操作分组，
例如编写代码、开发容器/控制器、设计模型推理成本和记忆、管理质量体系等。
为整个来源类别明确列出成员，编译时拒绝遗漏、重复和未知成员，不按测试题临时分配。
目录描述写操作和交付物；更小的可选分组列出全部子范围名称，避免只列几个代表词。
最终选择仍读取所有保留能力的原始完整描述。

树共 207 个节点，静态覆盖 376/376，最深五层，末端单组不超过四项。
静态覆盖仅说明没有漏建节点，不证明模型永远不会选错分支。

三个方案共用同一棵树、同一原题、同一描述和门槛：

- **固定两层**：筛过根类和来源类就尝试终选。超过 96 项明确停止。
- **一直下钻**：继续筛每一层，直到所选分支全部抵达末端，最多六次目录判断。
- **自适应**：总候选不超过 24 项时优先终选；单个已选分支不超过 8 项时先完整保留，
  不反复询问它；其他分支继续展开。全部分支都已足够小时，在 96 项上限内终选。
  因此本轮两题的终选列表仍有 58、55 项，并非强行截成 24 项。

自适应还实现了一个保守的描述长度估计：候选不超过 48 项时，若再看目录的估计字符量
已经达到直接终选的 65%，就提前终选；每次加入 800 字符作为请求开销估计。
这是预先固定的启发式，不是测得的 token/延迟模型。本轮真实样例没有走到此分支，
只通过了专门的离线检查，不能用它解释本次收益。

目录门槛随节点深度依次为 **0.2、0.3、0.4、0.45**，最终选择仍要求 **至少 0.7**。
多项明确要求可保留多个分支。连续两步不缩小且候选仍超过 96 项时停止；
不截断候选、不回退全量、不重试或更换提供方。没有给原题添加固定英文摘要或指定能力名。

实际观察到的路径：

```text
供应商评分：376 → 158 → 16 → 终选       （2 次目录判断）
集群控制器：376 → 149 → 143 → 49 → 23 → 终选（4 次目录判断）
```

这些是本轮实际候选数。不同需求走不同深度，树本身没有在查询时重写。

## 真实对照

先冻结八题、分类、代码哈希、顺序和预算。先测费用优化与集群控制器两题；只有自适应
两题都选对、各步保留正确能力且能终选，才继续其余题。小样门槛通过后才扩大。
每题轮换方案顺序，每阶段只发一个新的无历史 Jev CLI 请求。标准答案不进入请求。

下表仅比较三个方案都完整运行的相同五题：费用优化、集群控制器、供应商评分、
应用内升级提示、财务模型。成功要求选对当前目标且没有丢掉所需能力。

| 方案 | 成功 | 平均筛选时间 | 平均总 token | 平均 Jev 请求 |
|---|---:|---:|---:|---:|
| 固定两层 | 2/5 | 1.83 秒 | 3,907 | 2.4 |
| 一直下钻 | 5/5 | 3.46 秒 | 10,788 | 5.6 |
| 自适应 | 5/5 | 2.69 秒 | 10,024 | 4.2 |

固定两层有三题因候选过多而停止，不能把这些低成本未完成结果当作效率优势。
这五题都保留了正确能力，但保留能力和最终成功是两个指标。

自适应与一直下钻逐题比较：

| 需求 | 深层时间/token | 自适应时间/token | 自适应终选候选 |
|---|---:|---:|---:|
| 中文费用优化 | 4.03 秒 / 15,909 | 3.09 秒 / 15,959 | 58 |
| 同义表达的集群控制器 | 3.36 秒 / 8,812 | 2.65 秒 / 9,562 | 23 |
| 中文供应商评分 | 3.81 秒 / 9,793 | 1.63 秒 / 6,046 | 16 |
| 同义表达的升级提示 | 3.38 秒 / 14,398 | 4.11 秒 / 14,161 | 55 |
| 中英混合财务模型 | 2.74 秒 / 5,030 | 1.99 秒 / 4,393 | 5 |

少一次目录判断可能让最终列表更大，费用优化和控制器题的 token 就略有增加。
升级提示题的耗时也没有下降。单题的网络/调度延迟不稳定，不能承诺每题都更快。

第六题“先 Jira、再 ISO 13485 QMS”中，自适应用四次目录判断加一次终选，
耗时 3.70 秒、10,641 token，最终保留 25 项；选中当前 Jira 目标，同时保留 QMS 目标。
固定两层超限；深层方案完成两次目录请求后遇到全局预算停止，不能计为语义选择失败。
因此该题不放入上面的五题平均对照。

## 为什么 token 降幅需要收紧解释

逐次核对相同请求的内容哈希后，发现 15 组重复输入中 14 组的分数发生变化，
其中 1 组跨过保留门槛，改变了实际候选集合。这一组属于供应商题：完全相同的目录请求，
两层筛选后一次留下 16 项，另一次留下 56 项。

因此平均 token 下降 7.08% 不能全部归因于自适应停止。作为**事后敏感性检查**，
去掉供应商题后，其他四题的结果为：

| 指标 | 一直下钻 | 自适应 |
|---|---:|---:|
| 平均 token | 11,037.25 | 11,018.75 |
| 平均时间 | 3.38 秒 | 2.96 秒 |
| 平均请求数 | 5.5 | 4.5 |

token 几乎持平，时间约低 12.38%。这不是替换原基准，也不是新增独立验证。
目前应把候选作为“减少不必要目录轮次”的进展保留，不能宣称稳定同时优化全部指标。
后续需要用预先冻结的新题与重复测量区分停止策略收益和目录评分波动。

## 预算、未测范围与保护

预算预先设为 120 次请求、600 秒、调用前已知用量 140,000 token；一条正在执行的响应
可跨过用量上限。实际发出 **70 次请求，140,303 token**，其中输入 124,801、输出 15,502，
总运行段 46.47 秒。所有请求均有完成记录和用量；没有待确认发送、重放或额外追加。
协调 Agent、静态准备和分析的用量不包含在这些数字中，未测账单费用或后端模型修订。

两个负向控制“只记录引文”和“取消旧需求”未执行。多任务题的深层对照未完成。
不能宣称完整八题通过、覆盖新需求，或证明 Skill/插件/MCP 的实际接入和执行成功。

20 项相关离线测试通过，覆盖提前终选、固定深度、完整保留小分支和后续动作、
0.7 边界、估计读取成本、不缩小就停止、目录覆盖、畸形响应、超限和不可重放。
没有重跑原来已完成的业务任务。

另一个生命周期工作已把日常版本升级为 `0.3.71+creation.20261015`。本次在该版本存在后
记录保护快照，结束时核对 121 个路径（115 个发布文件及 6 个配置）一致。
没有覆盖该升级、修改正式目录、改日常连接、合并 main 或发布本次试验。

设计参考了 [Anthropic 关于明确描述操作边界并用任务评估工具的说明](https://www.anthropic.com/engineering/writing-tools-for-agents)，
实际收益只采用本机这轮记录，没有引用外部效果数字。
