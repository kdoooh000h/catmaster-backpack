# 普通需求自动获取新能力：真实 Agent 补测

2026-10-14。六条固定需求的完整目标达成率为 **1/6（16.7%）**。
这里的完整目标是：不提供能力名称，由 Agent 通过背包找到此前安装记录中
没有的能力，接入并实际完成任务。不能据此声称三类能力已全面自动打通。

另有一次隔离环境的工具授权配置错误，背包没有收到业务请求。它保留在完整
尝试记录中；包含它是 **1/7 次尝试通过（14.3%）**，没有用修复后的结果覆盖。

## 条件与范围

- 使用原生 Codex CLI `0.162.0-alpha.17.2`，沿用本机配置的
  `gpt-6-astra / xhigh`；实际服务端模型身份为 `unobservable`。
- 六条普通中文需求，每类两条。测试框架只指定 Skill、插件或 MCP 这一类别，
  没有给能力、发布者、仓库、包名或预设答案。因此，本轮测试的是类别内的
  自主发现，不是主 Agent 自主决定使用哪一类能力。
- 每条使用新会话、新 Agent home、新背包数据目录和空能力缓存。复制已有的
  七个公开来源的目录元数据，不复制能力包、使用历史、MCP 注册或私有 Skill。
- 安装基线检查了日常背包公开注册表、Codex/Claude/Droid/Qwen 的已知本地
  Skill 安装目录，以及已知公开插件安装/缓存记录。它不能证明整台电脑历史上
  从未出现过同名文件。新选中的 `internal-comms`、`playground` 均不在此基线。
- 使用已安装的市场网关及其现有 standalone 依赖，候选与阈值没有修改。
  只在隔离连接的 Jev 命令外增加原样转发的日志包装，取得实际 usage。
- 测试数据为构造的项目事实、代码及虚构人物关系。任务与规则保存在
  [测试脚本](../benchmarks/market-blind/run.py)；[方法说明](../benchmarks/market-blind/README.md)
  说明了授权、隔离和验收边界。

## 时间与 token 的口径

时间从每次原生进程启动到退出，包含模型启动、思考、选择、下载接入与任务
处理，不含预先制作试题、采集安装基线和根 Agent 的结果核对。六条顺序运行；
首条启动到末条结束的窗口是 831.609 秒，包含中间检查间隔。

六条的回执合计：主 Agent 输入 527,384、输出 10,958；Jev 输入 52,170、
输出 6,082，共 596,594 token。主 Agent 的输入中有 **406,016 缓存输入**，
已经包含在输入总数里，没有再相加。11 次 Jev 调用全部取得 usage，六次
原生回合都有最终 usage；知识关系任务存在 TLS 断流重连，失败网络请求
是否产生额外 token 无法核实，因此全窗口合计应理解为**已知下限**，不是账单。
费用未知，不根据 token 或模型别名估算费用。

首次工具授权配置失败耗时 90.683 秒，原生回执为 40,382 token，Jev 没有调用。
当时原生主机返回 `MCP tool call requires approval, but approval policy is never`，
协议日志确认没有 `tools/call` 发往背包。随后只对新的隔离测试连接采用正常的
逐服务器工具授权配置，保留 shell 写入沙箱并禁用无关原生能力。

包含这次失败，共七次原生启动，进程时间合计 **758.182 秒**，已知 token
至少 **636,976**。首次失败也出现 TLS 重连，未返回的网络请求用量保持未知。
完整运行窗口从首次失败启动到最后一条结束约 992.640 秒。根 Agent 的实验
编排、代码检查和写报告用量不在原生试题回执中，没有冒充已计入。

## 查清的断点

**插件模板确实存在，但资源候选漏掉了它。** `playground` 包已下载
`templates/concept-map.md`（3,644 字节）及另外五个模板。选定的插件 Skill
要求读取适合的模板，Agent 通过 `acquire_resource` 请求该文件，却立即收到
`none`。现有 standalone `core/jev_public_router.py` 的资源分支，对没有
`external_source` 标记的条目只考虑 `references/scripts/examples/assets/SKILL-topics`，
遗漏 `templates`。按实际包和这条规则检查，资源候选数为零；此次也没有发生
资源选择的 Jev 调用。这是可定位的资源暴露问题，不是文件未下载。

**两个需求在第一层来源选择就被挡住。** 代码审查与知识关系请求均只发生
一次 Jev 来源判断，返回 `none` 后直接结束，没有进入具体市场条目。共同
入口在 `Market.prepare → choose`：它把市场来源说明交给以“MCP service”
为目的的路由判断。当前证据确立了失败位置；名称/描述与判断提示的哪一项
导致这两次拒选，尚未通过受控对照确定。本轮没有改提示或重放以制造成功。

**时区请求的公开源访问失败。** 原调用只有 `SourceError`，具体底层原因
未透出。固定六条结束后，对同一公开 URL 做了一次只读诊断，仍在 12.521 秒
报 `TimeoutError: The read operation timed out`。这支持本机到该查询接口存在
连接或响应问题，不能据此确定是本地网络还是服务端故障。没有重放模型或
MCP 业务操作。登记库本身按名称子串搜索，见
[官方 API 说明](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/official-registry-api.md)；
本轮还没有成功验证从普通描述到新服务检索词、接入、执行的完整链路。

## 保留现有能力与验证

测试前后六个受保护配置/注册文件的字节一致：日常 Codex 配置、公开 Skill
注册、来源目录、MCP 注册、路由配置及 provider 环境配置。试验用临时 MCP
服务已停止，所有已接入测试包及证据留在隔离目录，没有导入日常背包。
原工作区未提交改动和 standalone 依赖没有纳入本次提交。

统计脚本的五项检查覆盖缺失 usage、缓存重复计数、无回复请求、同名既有
能力、TLS 重连后不能声称 token 完整。项目必需文件/JSON 和差异格式检查
通过；它们仅支持测试记录可靠性，不能把上表失败改成通过。输出验收由本
对话根 Agent 完成，没有声称独立人工审核。

原始协议、usage、输入、输出、安装基线、配置恢复材料和调用凭据保留在
用户私有 evidence 目录，未上传。公开仓库仅保存无密钥的脚本、测试和此报告。
