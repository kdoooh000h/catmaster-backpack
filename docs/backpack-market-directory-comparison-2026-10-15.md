# 市场描述与分类：同六题真实对照

2026-10-15。本轮实现了市场用途描述、标签复用和两到三层目录，并完成六条原普通需求的新旧对照。**严格完成从 2/6 到 3/6，但六题耗时之和增加 6.88%，双方完整计账的五题 token 增加 32.47%。当前证据不支持把新策略作为整体更优版本晋升到日常连接。**

此前 6/6 是跨版本、多次失败修复与续做的累计覆盖。本表是重新固定预算后的单次同题回归，不能直接与该累计覆盖比较。这六题参与了本轮调整，不是独立 holdout，也没有统计上的普遍优越性结论。

## 实现与实际取舍

- 复用市场的 category、tags、keywords，补入原先被入口遗漏的社区市场 `about` 用途说明。叶卡保留发布者原描述，明确指导、插件包和 MCP 服务的区别；包内真实依赖仍在后续核对。
- 共享用途目录涵盖开发质量、设计、写作、数据/知识关系、检索/时间、运维、安全、产品经营。来源 → 可选用途目录 → 能力，最多三层；小目录省略中间层。包内组件检查依据固定包内容进行。
- 缺少可复用标签的公开条目由 Jev 按元数据补主、次归属，接受门槛 0.4；同一条目可以多重归属。缓存绑定元数据、目录版本、类型与配置模型。尚未处理或判断不清的条目伴随每个被检查目录，未按用户需求关键词硬删。
- 补分类每批八条、每次最多 32 条，使用 18 秒预算；失败或未知请求不自动重放。完整插件元数据上限 1,000 条，单次能力选择上限仍为 192；超限明确停止，不截取前缀。
- **目录阶段默认 0.1，完整指导/真实工具核验至少 0.7**，并保留更严格的现有最终设置。试过的中间 0.3 门槛拦住了实际分数 0.29 的待查目录，因此最终回退到前宽后严的两档门槛；分数不是实测成功概率。
- 公开 Skill 的一个来源完成负判断后，最多检查三个来源；provider 错误和未知结果停止。已绑定插件不会借此搜索无关来源。权限、包指纹、实际入口、MCP schema、安装边界和调用回执仍由原运行时控制。

初版曾给来源目录附上宽泛的业务概述，使周报需求进入偏网页写作的来源；已撤掉该层泛化描述。另一个中间版在插件简介阶段弃权，后续改为紧凑的原始描述/标签，补上来源用途，并区分“值得检查”与“完整内容确实可用”的提问。失败与消耗全部保留，没有改成成功。

## 条件

旧侧冻结提交 `8cae551` 的适配层，新侧冻结 v6 的全部 `market_*.py`。最终源码另含非默认目录门槛继承、只允许公开来源元数据进入新分类器的保护修补，由单元检查覆盖；本轮原生实际使用的公开来源、0.1/0.7 配置及传给 provider 的值不变，没有为这些保护修补重复成功回合。用户自存/私有指导不参与新补分类。共用现有 standalone 依赖目录、保持只读，未对整个依赖目录做字节冻结。原生 CLI 为 `0.162.0-alpha.17.2`，两侧均配置 `gpt-6-astra / xhigh`；实际服务端模型与美元费用不可观测。

每题独立会话、home、背包和工作区；原六条中文普通需求逐字保留，评估器只指定 Skill/插件/MCP 类型，没有给能力或发布者名称。每次 360 秒、指示最多 12 次背包调用，无自动业务重试。原生被测 Agent 并发最多两个；外部负载和模型随机性仍可能影响结果。

四个成功读取后冻结的公开目录共有 **633 个市场条目**：Anthropic 315、OpenAI 180、wshobson 94、Trail of Bits 44。这不是 633 个独立、全新或可执行能力。两侧共享完整来源/精确查询快照，保留原观察时间；包、安装、授权、工作副本和业务数据重新建立。Registry 查询未成功，不能冒充成功完整快照。

新侧复制了另行计账预检生成的 **70 条公开分类记录**，没有复制包、计划、授权或业务结果。这是**部分分类缓存**，每题仍可能补分类，其消耗已包含在相应 Jev 数值里，不是完全温缓存。

时间是各题从原生启动到结束/超时的墙钟时间之和，包含失败等待；并非整个实验的用户等待时间。新侧增加 71.168 秒（6.88%）。两侧交互页均缺少 `turn.completed` usage，原生 token 为未知，表中该行仅为已知 Jev 下界。**只对其余五个完整计账的同题比较，旧 616,997 → 新 817,342，增加 200,345（32.47%）**；不能计算六题完整 token 增幅。

严格完成要求此前安装名单里没有的能力被实际接入/读取、应用，并在预算内完成原任务。安装名单来自已知公开安装/缓存根，不是全盘历史审计，也不能完全排除语义别名。评估为本轮主 Agent 核对产物、流量与执行记录，没有独立盲评审员。

## 已检查的内容与未验证范围

周报保留指定事实、负责人和期限。新主题使用 `theme-factory` 实际取得的三份主题资料，三套各有三色、用途、字体建议和两句应用说明；正文配色实算对比度为 5.3202、9.3820、12.5655。字体渲染和印刷未测试。

新审查由普通需求发现 `python-development`，使用初始名单里没有的 `python-testing-patterns`；旧侧使用 `superpowers` 的 `systematic-debugging`。两侧报告都实测复现运费参与折扣、空车收运费和超大整数精度边界，保留 `cart.py` 原字节。未把未规定的数量字段或舍入方式当成缺陷。新侧在 94 条来源目录中保留 38 条进入所选用途池，最终能力未被该池漏掉；这只是该题的观测，不是全目录召回保证。

新交互页在约 258.2 秒写出，Agent 随后说明将做自检，但 360 秒内未记录到自检执行/完整结束。因此严格失败。主评估器随后通过浏览器本地 HTTP 预览实测：k=16、m=4 时显示 3.142 s；实际复制 JSON 的 T 为 π，带正确单位；重置恢复 k=20、m=1、T=1.405。剪贴板已恢复，临时页面和预览服务已关闭。**浏览器工具禁止 file://，直接双击文件的运行未实测，也没有通过其他接口绕过限制。**

两项 MCP 都在本机读取官方 Registry 时超时/网络失败，未执行实际时区或知识关系业务调用。尚未查明链路还是服务端原因；这些结果不能证明 MCP 分类正确或错误，也不构成新版本 MCP 接入/执行验收。

四个非 MCP 需求都取得了符合用途的新指导，没有在这四题观察到最终目录漏选。MCP 两题受阻，不能声称已经满足对所有正确能力不漏选的要求。结构覆盖/保留 pending 的测试也不能代替语义召回实测。

## 消耗为什么增加

审查一题贡献了五题 token 增量的约 89%。其原生 Agent 从 174,673 到 235,827 token，Jev 从 34,198 到 151,798。新准备计划记录了 **18 次完整指导核验、14 次指导预选**，旧侧对应 3 和 4 次；两侧最终还选用了不同的指导包。目录缩小没有同时消除包内反复选择与完整内容核验，不能把成本变化只归因于目录卡片大小。

交互页从写出到超时还有约 102 秒，但日志不足以区分推理、传输等待或客户端原因。没有把全部无工具间隔计作模型推理。完整业务流程比单独 Jev 请求更慢，不能只展示短路由耗时。

额外诊断共四次原生回合和三次不执行业务的预检，**另计 1,301,324 个已知 token**。预检 v4：未准备成功，49.782 秒/127,623 token；v5：配置/适配仍不足，96.446 秒/174,394；v6：准备成功，63.890 秒/286,083，尚不算任务通过。v6 中补分类九次请求、70 条记录，93,875 token/5.844 秒 Jev 时间，已包含在诊断总额中，不另加一次。

加上新旧正式对照，本轮记录的原生/Jev **已知下界为 2,798,687 token**，还有两次原生超时消耗未知；根 Agent 编码、工具、网页/CUA 等消耗未统一计入，美元费用未知。额外阶段的时间存在并发和包含关系，不与各阶段 Jev 时间重复相加。
