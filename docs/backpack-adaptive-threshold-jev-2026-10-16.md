# 自适应门槛与 Jev 用法核对

本轮没有找到可以替换现有方案的新策略。保守自适应门槛未解决旧三步题的候选过多；
收紧目录问法虽然降低 token，却漏掉必需能力。继续保留上一轮描述修正、原目录问法、
当前步骤优先和最终 Choice confidence 0.7。实验代码与失败记录保留，不接入日常版本。

## Jev 用法：哪些正确，哪些需要改进

依据官方文档与本地 CLI/实际请求核对：

| 项目 | 核对结论 |
|---|---|
| 目录用 Noul，终选用 Choice | 合理。目录允许多个分支同时相关；终选只选择当前步骤的一个能力，并保留 none。 |
| 每层多问题合并 | 已做到。同层目录一次请求，共用原始需求和规则，没有每个目录单独发请求。 |
| 问题之间的依赖 | 同一批问题独立，没有让某个问题偷偷依赖另一个答案。选出分支后才决定下一层选项，这种跨请求依赖成立。 |
| 分数的含义 | 需要纠正表述。目录 Noul 是相关命题为真的概率，没有独立 confidence；最终 Choice 的 confidence 由选项概率分布计算。两者不是同一种分数。 |
| confidence 是否读错 | 上一轮 19 个终选回执与官方公式核对，最大差异约 0.00043，符合回执舍入。当前读取的是 confidence，没有误把最高概率当作它。 |
| 96 候选上限 | 是本项目的成本边界。官方 Choice 支持最多 255 个选项，但还受上下文限制；不能把本地超限称为 Jev 不支持。本轮没有提高上限。 |
| 模型版本可追溯性 | 仍有缺口：适配器未显式固定 model，也丢弃 CLI 返回的 model 元数据。本轮未读取账号配置，不能断言实际使用哪个版本。官方建议调过门槛后固定版本并记录响应版本。 |
| 进程与连接成本 | 每阶段启动一次 CLI；时间含进程、连接及提供方处理，不能把它都算成模型推理时间。持久连接收益本轮没有实测。 |

官方依据：[问题类型与批量问法](https://docs.typesafe.ai/primitives)、
[分数定义与公式](https://docs.typesafe.ai/confidence)、
[Choice 限制与层级分类](https://docs.typesafe.ai/primitives/choice)、
[模型版本与上下文限制](https://docs.typesafe.ai/models)。核对日期为 2026-10-16。
CLI 为 0.3.2，源码摘要在结果中；只检查代码和公开回执，没有读取密钥或改变模型配置。

官方[Skill suggestion 示例](https://docs.typesafe.ai/cookbooks/skill_suggestion)也采用先筛选、
后读更完整证据的方式；其目录规模、短名单规则和目标与本实验不同，不能直接搬用其
准确率或参数。此处继续使用既有分层目录，不恢复全量方案。

## 冻结的三组对照

三组共同保留全部 376 个能力、目录描述与归属、完整原始需求、当前步骤终选提示、
候选全文、最终 0.7、最多六轮目录和 96 个终选候选。没有固定英文摘要。

1. **现有方案**：目录 Noul 门槛 0.2 → 0.3 → 0.4 → 0.45，按原成本条件自适应展开。
2. **自适应门槛**：前两层不变。第三层以后，当保留候选仍超过 96，且相邻保留分数
   相差至少 0.12，才允许门槛最多提高 0.10。优先取能满足数量边界的最低门槛；
   无足够间隔就不调整。计数用成员并集，不将独立 Noul 概率相加为概率质量，也不强行取前 K 个。
3. **自适应＋收紧问法**：保留第二组规则，把目录问题改为结构化的“是否直接覆盖某项
   必需操作”，明确排除仅领域、词语或工具相近。目录说明原文、共享状态和终选不变。
   这组同时改变问法和结构，不能拆分归因给其中一项。

这只是待验证的启发式。分数出现间隔，并不证明低分分支没有必需能力。

先用旧回执做逐阶段离线试算：51 行、199 个目录阶段，仅触发一次，从 150 减为 110，
没有新增参考目标遗漏。这不是完整反事实终选，也不是新的准确率样本。
12 项离线检查通过，覆盖早期门槛、数量与分差条件、成员并集、保留后续小分支、
原始请求/全文、0.7 边界、未知发送停止、语义失败保留及不重发旧通过基线。

随后冻结一条旧三步失败需求与四条新组合：监控→经营分析→文化、渠道→故障响应→
知识库、审依赖→文化→欢迎邮件，以及取消财务/依赖但保留产品发现→项目跟踪。
旧题已有通过的“只补描述”基线直接复用，只给两个新策略各一次实测；四条新题做
完整三组、轮换顺序。没有重跑此前通过的需求/策略组合。

预先限制为 98 次请求、380,000 token、240 秒；每次最多 15 秒，零重试。
实际完成 **14 行、68 次请求、267,977 token、45.065 秒**。没有超预算、未知发送、
传输失败或缺失用量。未在结果出来后调参或补跑。

## 新四题的同条件比较

| 指标 | 现有方案 | 自适应门槛 | 自适应＋收紧问法 |
|---|---:|---:|---:|
| 当前选对且全部必需能力全程保留 | **4/4** | **4/4** | 3/4 |
| 平均选择时间 | 3.528 秒 | 3.038 秒 | 2.943 秒 |
| 时间中位数 | 3.257 秒 | 3.075 秒 | 2.988 秒 |
| 平均报告 token | 21,790 | 20,981 | 15,201 |
| 平均调用次数 | 5.00 | 5.00 | 4.75 |
| 平均最后候选数 | 64.75 | 61.50 | 33.25 |

**本轮真实调用中，自适应门槛一次都没有触发。** 第二组表面的 token −3.71%、时间
−13.87% 不能归因于门槛优化；其差异来自独立评分路径和调用耗时波动。用四条基线
的既有回执再做精确离线回放，新旧遍历的 20 个请求与结果完全相同，新增网络请求为零。

收紧问法组 token −30.24%、时间 −16.58%，但发生遗漏和一次不符合预设参考目标的
接受，不能当作同等准确率下的节省。所有失败均计入分母。

## 旧失败项与新遗漏

旧题是“当前公司财务，随后依赖审查，再做知识库”。此前描述修正组保留 93 个候选
并通过，该回执只作历史参照，不混入本轮四题时间/token 平均值。

- **自适应门槛**：保留全部目标，但最终有 105 个候选，超过 96，未发终选请求。
  第三层相邻分数为 0.49/0.60，间隔 0.11，小于预先设定的 0.12；旧离线记录是
  0.47/0.63，间隔 0.16。第四层的较大间隔又超出了允许提高门槛的范围，因此没有调整。
- **收紧问法**：最终候选降到 55，当前财务能力以 0.98 选对，但知识库所在第一层
  目录只得 0.18，低于 0.2，后续能力已遗漏。
- 新“监控→经营分析→文化”题中，收紧问法使监控所在第三层目录得 0.34，低于 0.4。
  后续终选以 0.92 选了通用 CTO 顾问，未命中预先指定的监控专用能力。没有实际执行
  来判定该替代项是否等价，故不能改判通过。

两种新策略包含旧题后的严格结果分别为 **4/5、3/5**，都不符合五题全部通过的验收。
问题不在于把 0.7 改低：正确选项已被目录阶段删掉时，剩余选项仍能获得高置信度。
当前证据支持区分“目录可能包含所需能力”和“具体能力直接完成当前工作”，但尚未
验证一种兼顾召回与成本的新问法；不能据此宣称整个 Jev 用法已最优。

## 验证、保留与边界

68 对 pending/done 回执、13 次实际终选、逐阶段原始需求/问题/完整描述、候选并集、
门槛、判分和用量全部核对。源码、输入和 CLI 摘要与冻结计划一致。验证时 354 个
发布/配置文件、主工作区 228 个文件及另一生命周期工作区 224 个文件、两者 HEAD
和 Git 状态均与本轮起点一致。没有日常安装、私有目录、生命周期或其他工作区改动。

保留现有描述修正方案；两个候选仅保留实验代码与失败证据，不提升为默认。96 候选
边界仍未解决。后续若继续，应先补齐模型版本记录，再考虑把当前选择与后续保留拆开，
而不是为了降到 96 就不断抬门槛；这些尚未实施或验收。

本次为实现者编写的四条新组合和一条已知边界题，各一次模型采样，没有独立盲测。
准确率只指预先定义的目录选择/目标保留，不包含安装、插件/MCP 执行或日常 Agent
业务完成。时间/token 仅覆盖 Jev 选择，主 Agent 与意图入口成本不在表中；实际模型
后端版本和金额不可观测。
