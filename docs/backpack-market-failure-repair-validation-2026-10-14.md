## 判据与测试条件

只有此前未安装的新能力实际完成原任务才通过。接入成功、返回指导、低成本选择诊断和 Agent 自报 completed 都不等于任务完成。插件必须检查实际使用的组件，不能仅凭插件包名是新的就通过。

原生 Codex CLI 配置仍为 `gpt-6-astra / xhigh`，普通需求文本与原版逐字一致；测试框架固定类别，不指定能力、插件、包或工具名。后端模型身份和美元费用 `unobservable`。每次独立原生 home、工作区和背包数据，最多 360 秒/12 次背包调用；知识关系的后续回合明确复用同一已写入的数据，只做未完成查询，不重新安装或写入。不是 VM 或对抗性读隔离证明。

## 为什么时间和 token 高

1. **多次完整失败复测是实际开销。** 本轮主题 6 次、插件 4 次、知识关系 7 次，17 次进程时长合计 1,559.556 秒（26.0 分钟）。前三类旧的成功任务没有重跑；这 17 次也不是 17 个独立题目。新增能力检查此前放在最后，导致 r24 产物做完后才发现所用指导早已存在，新增测试门槛就是为避免再次浪费。
2. **主 Agent 的上下文被多步反复计入。** 原生输入 1,616,614、输出 34,451 token，其中输入的 1,407,616 是缓存输入（输入的 87.1%），未缓存输入 208,998。主 Agent 共 1,651,065 token，占本轮原生流程总 token 的 85.3%。缓存输入不是新生成内容，也不能与未缓存输入按同一价格推算；实际美元账单未知。不能只凭这些日志归因于 `xhigh` 或某个后端模型。
3. **Jev 不是时间的主要部分，但检查也有成本。** 原生流程内 Jev 输入 254,052、输出 30,792，共 284,844 token；87/87 次均有 usage。Jev 累计 59.730 秒，背包工具等待 274.166 秒，二者包含在原生时长内，不能相加。原生时长扣除背包等待还有 1,285.390 秒，包含主 Agent、工具编排、普通命令及其他未细分开销，不能全部标作模型推理时间。
4. **外部读取确有等待。** 官方 Registry 功能词搜索超时、插件元数据/归档读取以及匿名 GitHub API 限额都产生过等待。r14 的背包等待为 68.089/167.836 秒。修复了有界等待和可说明来源的缓存，但没有证明官方服务稳定可用。
5. **候选诊断另计，不能藏在“没跑完整 Agent”后面。** 低成本预检和选择诊断仍有 225 次 Jev 请求，共 958,031 token（868,656 输入、89,375 输出），225/225 有 usage，Jev 时长 204.442 秒。12 个完整预检记录合计 488.164 秒，均零业务调用；r13 四次附加就绪诊断另有 43.196 秒，其 token 已包含在同一日志中，只算一次。资源路径诊断 2.828 秒有真实 Jev 调用但缺 usage，因此总用量仍是下限。诊断时间与其中的 Jev 时间重叠，不相加。

本轮原生流程已知 **1,935,909 token**；加上独立诊断的已知部分为 **≥2,893,940 token**。根 Agent 的分析、改代码、子代理、网页读取及编排不在这些日志中，不能声称是整段对话的完整消耗或费用。

已经实施的节省包括：不重复在 Jev state 中发送候选描述；复用严格 MCP 校验；包归档在同次准备内复用；市场等待有界；首次工具不合格时在背包内部继续检查，不必重新开完整 Agent；已完成业务不重放；将新组件资格前置。更完整的校验和候选回退也可能增加 Jev 消耗，因此没有宣称全部指标同时下降。

## 与上一轮对照的边界

[上一轮](backpack-market-lifecycle-validation-2026-10-14.md)是 16 次、六种任务，2,088.825 秒、2,178,336 token，累计完成 3/6。本轮只测三个未完成项，条件和次数不同，不能把总量更少解释成同条件优化。

同一个主题需求从旧首测失败的 47.473 秒/56,787 token，到这轮真正完成的 142.949 秒/170,837 token，准确完成的代价更高。知识关系从旧首测失败的 160.969 秒/143,110 token，到写入和全部续查 556.985 秒/608,738 token，也没有证明更快更省。插件还没有合格的新能力完成样本。结论是**可靠性和诊断可解释性有进展，最低时间/token 尚未达成**，不能用失败早退的数据证明等质量节省。
