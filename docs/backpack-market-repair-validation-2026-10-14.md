# 普通需求盲测：发现断点修复与对照

2026-10-14。沿用上一轮六条普通需求，不给能力名称。按“日常安装基线中没有、
由 Agent 发现接入、实际完成任务”的同一标准，完整成功由 **1/6 提升到 2/6**。
新增成功是插件生成离线交互页面。两条 MCP 仍未完成实际业务调用，不能声称三类全面打通。

## 改动及其实际证据

- **模板入口**：市场插件没有公开 Skill 来源标记，原资源分支因此漏掉 `templates/`。
  新适配器从已经授权、指纹固定的插件包选择资源，复用路径和工作副本检查，
  不伪造来源登记。真实 Agent 自选 `playground` 后取得完整
  `templates/concept-map.md`，产出页面。根评估器在离线 Chromium 中检查滑块、
  周期公式、单位、重置和真实剪贴板 JSON，全部通过；没有外部网络请求或页面异常。
  受测 Agent 自己完成脚本检查，但没有成功启动浏览器，两种检查分开记录。
- **第一层选择**：目录使用“是否可能包含有帮助的能力”提示，插件使用插件提示，
  不再让市场来源套用具体 MCP 服务问题。阈值保持目录 0.1、最终至少 0.7。
  代码审查补测中，来源置信度 1.00、分类 0.85、插件 0.88，越过了先前第一层
  `none`，选中 `coderabbit`。随后明确返回当前适配器需通过原生宿主处理该外部插件来源，未接入或伪装执行。
  页面插件实际经过来源、分类、插件三个目录决策，未新增全量兜底。
- **MCP 市场访问**：原先 12 秒读取上限不能容纳实际响应；本机曾在约 13 秒、
  30 秒取得同源成功响应，也多次超过 35 秒。不能把全部失败归结为单一服务端原因。
  初版加长等待后仍有超时，因此再使用本机 curl 的 HTTP/2 协商能力，禁用 curlrc，
  保留 HTTPS/TLS、响应大小和不跟随重定向的约束。没有改 DNS、系统代理或证书验证。
  最后时区补测能够读取市场、发现宽泛搜索结果过多、缩小功能词，并到达最终选择；
  该选择置信度为 0.44，仍按原阈值停止。访问恢复的样本不等于服务可用性保证。
- **名称搜索适配**：官方接口按名称子串搜索，不能直接当作语义搜索。现在按一至四个
  功能词取并集、完整分页去重；每词最多六页、最终最多 192 项，超界明确停止，
  不从截断的第一页选能力。只读 GET 有总预算和最多一次读失败重试；接入与业务调用
  继续使用原来的回执约束，未重放已完成或不确定的操作。

依据：[官方 Registry API](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/official-registry-api.md)
说明名称子串查询和分页；[维护者仓库的延迟问题记录](https://github.com/modelcontextprotocol/registry/issues/1252)
提供相似背景。上述本机成功、失败和耗时来自本轮实际请求，不以社区报告替代根因证据。
