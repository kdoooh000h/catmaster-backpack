# 主 Agent 上下文与调用衔接对照

2026-10-15。只使用原来的弹簧单文件网页题，未重跑其他五道已通过题目。能力选择、目录、完整指导和最终 0.7 门槛的实现均保持不变。

本次减少了一部分重复上下文：最终主 Agent 总 token 从 122,929 降到 103,882（15.49%），主 Agent 加 Jev 从 169,740 降到 156,753（7.65%）。**没有取得提速：164.759 秒变为 245.415 秒。** 主 Agent 非缓存输入和输出反而增加，不能由总 token 下降推断费用下降。

## 查到的开销

上次完整运行有 7 次可观察的模型用量更新，每次输入分别为 12,159、14,212、15,148、17,228、19,842、20,363、20,568 token。合计输入 119,520，其中缓存输入 103,168，非缓存输入 16,352；另有输出 3,409。缓存输入是输入子集，不重复相加。

这些轮次对应：读取全部背包工具说明、准备、连接并获取指导、写 HTML、真实浏览器验证、上报、最终回答。第一步把整份背包工具元数据打印进上下文；完整工具目录为 10,246 字符，其中描述 7,194 字符。连接结果 7,873 字符，其中指导正文 3,878 字符；其余包含来源、句柄、范围及操作说明。这些说明和之后生成的 HTML 会继续留在后续模型输入中。

正文不能为省 token 而截断；目录选择也不是主耗时。上次准备与连接共 9.836 秒，浏览器工具等待 50.768 秒，其余 104.145 秒包含模型推理、代码生成及宿主调度，不能全部解释为纯模型算力耗时。生成页面那轮从前一工具结果到文件写入约 64 秒。大量总 token 是历史上下文的重复处理；实际时间还取决于生成量与浏览器回传。

## 保留的改动

- 精简工具描述，所有入口仍保留；完整工具目录从 10,246 减至 7,931 字符，描述从 7,194 减至 4,675（减少约 35%）。通用范围说明在选中指导时提供，不在两个工具描述中重复整段展开。字符数不冒充 token 数。
- `prepare_market_capability(connect_guidance=true)` 可以组合现有准备、连接、完整指导与资源读取。默认关闭，仅用于调用者已获授权、最终适配已通过、只有一个指导组件且没有 MCP 服务的插件计划。混合计划和其他类型仍返回预览。原连接继续检查范围、包指纹、失效/撤销状态并保留备份；不运行包代码，不把选择当作许可。
- 准备后出现失败或状态改变，保留原计划句柄并要求核对，避免调用者丢失中间状态后重复准备/安装。连接成功而读取失败继续保留已连接事实。
- 对支持代码组合的宿主，明确衔接“文件写入成功 → 验证实际结果 → 上报”，不为传递写入成功单独增加模型一轮。未知结果停止；未检查不能报告完成。

没有修改 `market_routing.py`、`market_guidance_fit.py`、`market_directory.py`、`market_connect.py`、`market_gateway.py` 的字节。保留上轮语言样本证据，本轮不重新跑选能力题库。新增参数没有绕过原先的 0.7 判断或把英文摘要固定到请求里。

参考 [Anthropic 的工具组合说明](https://www.anthropic.com/engineering/advanced-tool-use)：程序可以衔接确定步骤，减少返回模型的中间结果；本次使用本地宿主现有代码调用能力，没有引入其专用 API 或借用文章的收益数字。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)用于保留工具 schema、边界说明和结果语义。

## 同题实测，保留两次结果

使用独立原生会话、工作区与背包存储。同一中文用户题、同一原生测试 policy、`gpt-6-astra / xhigh`、CLI `0.163.0-alpha.10.2`、初始 70 条分类、公开目录快照和浏览器桥接器。均排除日常已安装能力，均选到新插件 `playground`，最终置信度 0.98、最低门槛 0.7。

两轮均没有固定英文摘要或能力名称。第一轮 Agent 自行写中文需求；第二轮自行写英文需求和通用搜索词，又额外询问一次学习模板。自然生成的需求、路由路径和页面代码并不相同，因此不是所有因素完全恒定的统计 A/B。

第一次省掉单独连接请求，但写文件、验证和上报仍分开；浏览器超过 60 秒后增加一轮等待，抵消了省掉的一轮。非缓存输入减少 33.5%，主 Agent 总 token 只降 1.0%。不能把这轮较好的缓存情况与第二轮较少的总 token 拼成一组优势。

第二次确实在同一次代码调用中执行了 `apply_patch → verify_local_webpage → report_skill_use`，使用实际验证结果决定上报状态。浏览器仍触发一轮等待，另有一次无结果的模板读取；最终模型用量更新只从 7 降至 6。背包实际调用仍为 4，不能宣称最终变为 3。

## 为什么时间仍高

第二轮准备阶段为 24.229 秒，额外资源读取 1.200 秒，浏览器等待 73.715 秒，上报 0.004 秒，其余 146.267 秒。相较基线：

- 自动生成的英文表达走了更多候选检查，排除了缺少宿主组件、组件超限或运行条件不满足的候选，再选中目标。Jev 从 10 次增加到 17 次。保留这些拒绝，没有为了提速漏查运行条件。
- 已返回没有选中补充资源后，Agent 又换了模板问法请求一次，仍返回 none。增加了一次资源请求和模型往返。这不是新的成功能力，完整计入成本。
- 第二轮生成的 HTML 及调用组合代码更多。生成最终执行块约 109 秒，输出这一轮为 3,965 token；基线写入轮为 2,590 token。衔接省了往返，但生成额外的组合代码、页面内容及自然推理波动仍会抵消时间收益。
- 真实浏览器操作记录为第一轮 18.229 秒、第二轮 18.108 秒，而工具等待约 76 秒和 74 秒。差额包含宿主接手、观察、控制和传回验收的间隔。它计入任务时间，但不等于浏览器运行本身，也不能归因于 Jev。第二轮文件观察器只复制已产生的测试产物，未代写网页、检查结果或使用记录。

当前剩余问题是重复补充资源请求、原生基础上下文、代码生成量和宿主验收回传，不能靠继续压低选择门槛解决。本轮没有继续增加提示规则或更多实测来追逐一个更漂亮的数字；不宣称已得到最快、最省费用的方案。

## 验收、总消耗和边界

两轮均真实拖动 k、m 滑块，核对三组公式值、点击重置，并读取复制按钮写入的实际剪贴板 JSON；均通过。页面通过 localhost 打开并阻断外部请求，`file://` 未直接验证。截图和与文件哈希绑定的验收回执保留在本地；用户剪贴板已恢复。浏览器桥接器属于测试设施。

Agent 在检查之后自行上报，两个隔离存储均存在 `agent_reported/completed`；评估端未补写。198 项相关本地测试通过，无跳过；项目必需文件、JSON、语法与 diff 检查通过。低成本阶段没有调用模型或执行其他业务题目。

两次原生测试合计 **325,216 已知 token**，包括主 Agent 225,600 和 Jev 99,616；共 27 次 Jev 请求。宿主协调与真实浏览器控制的 token 为 `unobservable`，是额外未计量开销，不按零计算。所有尝试均保留，不只展示最终轮。

本任务未写日常 Agent 配置。结束核对发现日常 `~/.codex/config.toml` 在测试窗口内哈希发生变化，来源尚未确认，本任务没有覆盖或恢复它。其余 5 个受保护文件和公开安装清单保持一致。原生测试使用冻结的独立参数与存储；共享 standalone runtime 并非完全字节冻结，因此也不能把测试当成完全隔离的运行时 A/B。

两个专用浏览器标签页、预览服务均已关闭，隔离数据保留；其他工作树改动不纳入本提交。没有升级日常安装版或合并 main。
